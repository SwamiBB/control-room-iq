# Contributing

Thanks for working on Control Room IQ. This page covers how to get running, how changes get in, and the rules
every change keeps.

## Ground rules

- **No proprietary code and no real data.** Everything in the repo is our own code or an open-source library
  listed in [THIRD_PARTY.md](THIRD_PARTY.md). Match, tracking and club data is synthetic and comes from the
  simulator; never add real fixtures, players, broadcast feeds or logos. Every PR confirms this in its template.
- **A person fires every graphic.** Don't add an auto-approve path, a bypass flag or a timer that airs
  something. `OverlayPacket` requires an approval, and the tests in `services/api/tests/test_gate.py` keep it
  that way.
- **Numbers from code, words from models.** Agents may quote numbers from match state but never compute them.
  New stats go in `services/ingest`, not in a prompt.
- **No secrets.** Everything authenticates with Entra ID (managed identity in Azure, `az login` locally).
  Don't add keys, connection strings or `.env` files to the repo.
- **The schema is a contract.** `packages/schemas/crq_schemas` is shared by every service and the web console.
  Change it in its own PR, agreed with the schema owner, and update every consumer in the same PR.

## Get it running

Full steps, including the Azure sandbox, are in [docs/SETUP.md](docs/SETUP.md). You need Python 3.12 and
Node 22, the versions CI and the images use. The short version, with no Azure needed:

```powershell
python -m venv .venv; .\.venv\Scripts\Activate.ps1
pip install -e ".[dev]"
Copy-Item .env.example .env            # CRQ_OFFLINE=1: agents use their offline fallbacks
uvicorn api.main:app --reload          # API on :8000; keeps running in this terminal
```

Then, in a second terminal:

```powershell
cd web; npm install; npm run dev       # console on :5173 -> /operator and /viewer
```

`CRQ_OFFLINE=1` is a first-class mode, not a test hack: the demo has to survive a model outage, so every
feature works offline, with templates in place of model output.

## Before you open a PR

Run what CI runs (`.github/workflows/ci.yml`):

```powershell
ruff check .                           # lint, line length 120
$env:CRQ_OFFLINE = "1"; pytest -q      # Python tests, no Azure calls
cd web; npm test; npm run build        # web tests and type check
```

Run `ruff check .` on its own, not piped into another command: a pipe hides its failing exit code.

Add a test with every fix, and check that it fails without the fix. Tests use small synthetic events (see
`services/ingest/tests/test_match_intel_units.py`) or the seeded reference matches; never a live service.

CI also builds the container images and checks that they run as non-root. CodeQL and Trivy scan every PR.
Dependabot only keeps the SHA-pinned GitHub Actions current; it doesn't update Python or npm packages. If Trivy
flags a dependency, add a version floor with the advisory ID in `pyproject.toml`, as the `urllib3` and `msgpack`
lines do.

## Branches, commits and pull requests

1. Branch from an up-to-date `main`: `feat/…`, `fix/…`, `docs/…` or `infra/…`.
2. Keep each PR to one change. Unrelated fixes go in their own PR.
3. Write commit messages as a short sentence saying what changes and why, e.g. "Keep every trace: the default
   sampler dropped an operator's fire".
4. Open the PR with the template: what, why, how to verify. Link the issue with `Closes #N` so it closes on
   merge.
5. Every PR is reviewed before merge. Answer each review comment with a fix or a reason, then ask for another
   look.
6. PRs are merged into `main` with a merge commit, and `main` must stay green: the live demo is deployed from
   it (`.github/workflows/deploy.yml`, run by hand).

If you touch a file another teammate owns, say so in the PR description so they can review that part.

## Docs

Keep the docs to what the code does today. If something is planned but not built, say "deferred" rather than
describing it as working. Reviewers check claims against the code and `infra/`. When you change behaviour,
update the README, [SECURITY.md](SECURITY.md) and [docs/ENTERPRISE-OVERVIEW.md](docs/ENTERPRISE-OVERVIEW.md)
where they describe it.

When you add or upgrade a dependency, update [THIRD_PARTY.md](THIRD_PARTY.md). Only add libraries under a
permissive licence (MIT, Apache-2.0, BSD, ISC or similar); ask before adding anything under GPL, LGPL or AGPL.

## Synthetic data

All match data is generated by `services/simulator` from fictional clubs (`data/clubs.json`) and scripted
storylines (`data/storyline*.json`). The same seed always produces a byte-identical file, and a test fails if a
committed file drifts from what its seed generates.

```powershell
python -m simulator.cli reference                              # regenerate data/reference/ (events + tracking)
python -m simulator.cli view --seed 42                         # top-down preview of a reference match
python -m simulator.cli calibrate --out docs/CALIBRATION.md    # realism table over 200 seeded matches
```

If you change the simulator, regenerate the reference matches in the same PR and commit them. On Windows, check
`git diff` afterwards: line-ending changes alone are noise, so discard them.

## Security

Report vulnerabilities as described in [SECURITY.md](SECURITY.md), not in a public issue.
